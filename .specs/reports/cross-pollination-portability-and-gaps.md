## Recommended ports

### PORT-01 — Warm CI's Bun install cache (rank 1)

**Mechanism.** `.github/workflows/ci.yml:64-86` contains an inline comment (read directly) documenting the exact problem: "Bun's own install cache (`~/.bun/install/cache`, populated and read inside this same job — nothing here restores it from `actions/cache`) intermittently races the lifecycle scripts it feeds, and the casualty is always a native grammar" — with the specific gyp error signature quoted, and a named incident: "It took down the v1.4.0 release chain twice in one hour: CI run 30208529279 attempt 1, then publish run 30208930036, which left v1.4.0 tagged but unpublished." The current mitigation is reactive: `bun install --frozen-lockfile && exit 0` falling through to a purge (`rm -rf ~/.bun/install/cache node_modules`) and a serialized retry (`--concurrent-scripts 1`) on failure. This is the *exact same class* of problem cbm's `cache-warm.yml` (new, 123 lines, cron `17 2 * * *`) was built to solve — a package-manager/build cache that a cold CI runner never gets to reuse, racing a native-addon post-install step.

**Target files/layers.** `.github/workflows/ci.yml` (all jobs' "Setup Bun"/"Install dependencies" steps) — add an `actions/cache@v4` step keyed on `hashFiles('bun.lock')` (restore-keys falling back to the most recent `bun.lock`-independent key) wrapping `~/.bun/install/cache`, so a warm cache is available before the install step runs; optionally also a small scheduled/on-push-to-main job (mirroring cbm's `cache-warm.yml`) that populates the cache proactively so the *first* PR after a `bun.lock` change doesn't pay the cold-cache tax either.

**Why it matters here.** This is not a hypothetical port — massa-ai has already been bitten by exactly this bug class once, badly enough to leave a tagged-but-unpublished release. The fix is additive CI-only infrastructure with an existing manual fallback already in place as a safety net.

**Public-compatibility blast radius.** None. Pure CI infrastructure; touches no installer, hook, generated config, MCP tool contract, or REST endpoint.

**Deterministic verification.** Before/after: count occurrences of the `"::warning::bun install failed — purging..."` line across the next N CI runs (should drop to ~0 once the cache is warm); alternatively, time the "Install dependencies" step across consecutive runs and confirm it drops toward the warm-cache baseline once `actions/cache` reports a hit.

**Open questions.** Whether to also cache the compiled native tree-sitter `.node` addons themselves (higher risk — a stale native binary tied to the wrong Bun/Node ABI is a worse failure mode than a stale *source* package cache) — recommend caching only `~/.bun/install/cache` initially, not build output.

### PORT-02 — Type-enforced sanitization boundary on Passive Capture (rank 2)

**Mechanism.** ai-memory's issue #196 arc (`fe404c0` strip-first → `f28029c` double opt-in capture → `2a46387` type-enforced `Sanitized<NewObservation>` boundary, "parse, don't validate" applied to the privacy boundary) is the single most directly transferable idea named in the ai-memory report's own "Portable ideas" ranking (#1 of 20). massa-ai's Passive Capture pipeline (`HookService.validateEvent`, read in full at `packages/core/src/services/hooks/hook-service.ts:1-120`) validates event *shape* (kind, `projectId`, non-empty payload) and enforces a *byte-size* cap (`HOOKS_MAX_PAYLOAD_BYTES=65536`), but performs **no content-level redaction** of the payload before it reaches `ObservationStore.insert`. Confirmed by three independent greps: (1) no `Sanitized<` type exists anywhere in `packages/` (`grep -rn "Sanitized<\|type Sanitized\|class Sanitized"` — zero hits); (2) no `redact|sanitiz|scrub` call appears anywhere on the hook-ingestion path (`hook-service.ts`, `writer-queue.ts`, `observation-extractor.ts` — the only sanitize-adjacent hits repo-wide are `attribution-resolver.ts` and `compaction-snapshot-service.ts`, neither of which touches payload *content*); (3) the hook binary's own `sanitizeSessionId` (`apps/claude-plugin/hooks/massa-ai-hook.ts:48`) sanitizes only the session-id string for path-safety, not payload content. Per `FEATURES.md`'s own description, "Observations are stored raw in PostgreSQL and optionally consolidated into structured memories by an LLM bridge" — meaning this raw, unredacted persistence happens **regardless of whether LLM consolidation (default OFF) ever runs**, since consolidation is a downstream, best-effort step, not a gate on the initial write.

**Target files/layers.** New `packages/core/src/services/hooks/sanitize-observation.ts` (a `Sanitized<T>` branded type whose only public constructor scrubs known secret-shaped substrings — API-key patterns, PEM blocks, bearer tokens — mirroring the existing `sanitizeFilePath` primitive in `packages/shared/src/utils/sanitizer.ts`, which the CodeQL closeout (`CHANGELOG.md` 1.12.1) already hardened for path-traversal, showing the team already invests in this exact utility); change `ObservationStore.insert`'s parameter type in `packages/core/src/data/memory/observation-repository.ts` to require `Sanitized<NewObservation>`; wire the scrub step into `HookService.validateEvent` (`packages/core/src/services/hooks/hook-service.ts`) before the event reaches `WriterQueue`.

**Why it matters here.** massa-ai's README frames Passive Capture as the primary, default-recommended way memory "builds itself" — meaning this is not an edge-case feature but the main data-ingestion path for most installs. ai-memory needed a 3-PR arc to get this right (a narrower capture surface — only the assistant's final `Stop` message — vs. massa-ai's `post-tool-use` payloads, which routinely include full tool outputs and file contents, a *wider* secret-exposure surface).

**Public-compatibility blast radius.** Low: the wire shape of `POST /api/v1/hook` and `/api/v1/hook/batch` is unaffected (same JSON accepted); this is an internal storage-layer change, not a public API or MCP tool-contract change.

**Deterministic verification.** Unit test: POST a payload containing a synthetic secret-shaped string (e.g., `sk-` + 40 hex chars, or a `-----BEGIN PRIVATE KEY-----` block) and assert the persisted row's payload has it redacted while ordinary code/text content passes through unchanged; a type-level test (`// @ts-expect-error`) proving `ObservationStore.insert` rejects a bare `NormalizedEvent`.

**Open questions.** Exact redaction rule set (regex-based vs. entropy-based secret detection) needs its own design pass — get this wrong in the direction of over-redaction and legitimate code snippets (e.g., a real `sk-` prefixed variable name in source) get mangled, which is exactly the risk ai-memory's own Antigravity capture regression (`94e0f5c`→`6451beb`) illustrates for a related but distinct mechanism (over-broad content-extraction, not redaction) — scope the first cut narrowly (recognizable credential *shapes*: JWT, AWS key prefixes, PEM headers) rather than attempting general PII detection.

### PORT-03 — Count-bounded security-allowlist gate for dangerous primitives (rank 3)

**Mechanism.** cbm's own "Portable ideas" list ranks this second: `NETWORK:file:function:expected-count:justification` / `WRITE:file:expected-count:justification` — a gate that fails when the *actual* occurrence count of a dangerous primitive diverges from a declared, justified count, catching any *new* unreviewed call site automatically rather than only checking allowlist membership. massa-ai currently has no equivalent: `oxlint`'s `correctness` category (the only enabled category, per `CLAUDE.md`) does not reason about "is this a new, unreviewed `child_process.exec` call" at all.

**Target files/layers.** New `scripts/check-security-allowlist.ts` + `scripts/security-allowlist.txt`, enumerating: `child_process.exec/spawn` call sites (expected: the ones inside `packages/core/src/controllers/executor-controller.ts` and `packages/core/src/services/executor/executor.ts`, which already implement the documented "local-dev only" sandbox trust model), raw template-literal SQL construction outside Prisma's parameterized query builders, and `eval(`/`new Function(` anywhere (expected: 0). Wire into the `build` CI job beside `oxlint`.

**Why it matters here.** massa-ai ships `execute`/`execute_file`/`batch_execute` as first-class MCP tools that run arbitrary user-supplied code on the host (`FEATURES.md` §Code Execution: "Trust model: local-dev only... NOT OS-level isolation") — a considerably larger and more consequential attack surface than cbm's entire coordination daemon, yet has no automated gate today that would catch a *new*, unreviewed dangerous call site being added elsewhere in the codebase (e.g., a future contributor adding a second `child_process.exec` outside the sandboxed controller).

**Public-compatibility blast radius.** None — an additive CI check, no runtime behavior change.

**Deterministic verification.** The gate is self-verifying: inject a new unreviewed `child_process.exec(` call on a scratch branch and confirm the gate fails naming file+line; revert and confirm it passes.

### PORT-04 — Close (or explicitly accept) the `RUN_POSTGRES_TESTS` CI gap (rank 4)

**Mechanism.** The grep-sweep agent confirmed, by direct inspection of `.github/workflows/ci.yml` (zero matches for `RUN_POSTGRES_TESTS`, cross-checked via `rtk proxy grep`) versus `.github/workflows/coverage.yml:95` (`RUN_POSTGRES_TESTS: "1"`), that **only `coverage.yml` sets this variable**. `scripts/check-coverage.ts:402-412`'s own comment states "50 of core's suites are wrapped in `describe.skipIf(!DEDICATED_DB)`." Since `ci.yml`'s Postgres service runs on the ordinary `localhost:5432/massa_ai` (not the dedicated `127.0.0.1:5433/massa_ai_test` `isDedicatedDatabase()` requires), `ci.yml`'s own `bun run test` step structurally cannot exercise those ~50 suites — the *primary, blocking, per-PR* gate is blind to them, and the entire safety net for that code rests on `coverage.yml` alone, a workflow `CLAUDE.md` documents as deliberately isolated from `ci.yml` for an unrelated reason (not extending the `release.yml` `workflow_run` trigger chain). Nothing in the repo suggests this specific *consequence* (main gate blind to 50 suites) was a reviewed, accepted trade-off rather than an accidental byproduct of the isolation.

**Target files/layers.** Either (a) also set `RUN_POSTGRES_TESTS=1`/point at a dedicated DB in `ci.yml`'s test job (cost: redundant DB spin-up, more CI time, and care needed not to accidentally couple `ci.yml` back into the release-chain-triggering concern `coverage.yml`'s isolation exists to avoid), or (b) — cheaper and arguably more honest — add one sentence to `CLAUDE.md`'s CI-gates section stating explicitly that `ci.yml`'s `bun run test` does not exercise `DEDICATED_DB`-gated suites and that `coverage.yml` is the sole correctness gate for that subset, so a future reader doesn't have to rediscover this the way this audit did. The durable structural fix, matching cbm's `test_venue_parity_contract.sh` mechanism, is a small script that walks `.github/workflows/*.yml`, extracts each workflow's test-invocation environment, and asserts any semantic divergence between them is either identical or named in an explicit, justified exception list (same idiom as PORT-03's allowlist) — so the *next* silent divergence between two CI workflows is caught mechanically instead of by a manual audit.

**Why it matters here.** This is the single most consequential newly-found defect in this report (see DB-07) — a real, structural blind spot in the gate every PR must pass, not a documentation nit.

**Public-compatibility blast radius.** None (CI-only).

**Deterministic verification.** For option (a): confirm a deliberately-broken `DEDICATED_DB`-gated test now fails `ci.yml`'s own `test` job (today it would only fail `coverage.yml`). For the general parity-contract mechanism: inject a synthetic divergence between two workflow YAMLs' env blocks in a scratch copy and confirm the new check flags it.

### PORT-05 — Name the revert-with-tripwire-test pattern as a documented practice (rank 5)

**Mechanism.** massa-ai already has an excellent instance of this governance pattern (see A-07: `llm-env-prefix.test.ts`), but it exists as tribal knowledge in one test file's header comment, not as a named rule anyone would think to apply the *next* time a compatibility boundary is retired. Given massa-ai's own history includes two successive project-identity renames (`massa-th0th`→`massa-ai`, and the `RLM_LLM_*`→`MASSA_AI_LLM_*` env-prefix retirement) plus `CLAUDE.md`'s explicit warning that residual naming drift is an ongoing, actively-managed risk ("Naming divergence (read first)" section), a future third rename is a *when*, not an *if*.

**Target files/layers.** `CONTRIBUTING.md`, under "Step 6: Invariants" (the existing 7-step managed-harness protocol already requires "fail loudly... never silently violate an invariant" — this is a one-paragraph, concrete extension of that same step): "When retiring a compatibility boundary (env-var prefix, config key, feature flag), assert **both** directions in one test: the new name reaches its target, **and** the old name has zero effect. A suite that only checks the new name still passes if the old one is silently left wired up beside it (see `llm-env-prefix.test.ts` for the reference shape)."

**Why it matters here.** Essentially free (a documentation paragraph, not new code) and directly forecloses a recurrence-prone mistake class this exact repo has direct history with.

**Public-compatibility blast radius.** None.

**Deterministic verification.** N/A (process/documentation change) — the test for whether it "worked" is whether the *next* compatibility-boundary retirement PR includes a two-directional test without being asked.

### PORT-06 — Capability-predicate prep for a future managed-harness host (rank 6)

**Mechanism.** ai-memory's Kimi Code and Grok Build CLI adapters both needed the same underlying fact modeled explicitly: different agent hosts have different lifecycle-hook quirks (some discard `SessionStart` stdout entirely, so handoff delivery has to move to `UserPromptSubmit` instead) — and ai-memory discovered this reactively, hardcoding the Kimi case first (`e2f5af9`, later corrected in `526f4bd`) before generalizing. massa-ai's four-host plugin architecture (`apps/{claude,codex,cursor,opencode}-plugin/`, generated by `scripts/generate-subagent-artifacts.ts`/`scripts/generate-skill-artifacts.ts`) is already the more general version of what ai-memory built ad hoc per host — the gap is that it has no explicit per-host *capability predicate* (e.g., "does this host inject a handoff on SessionStart, or only on UserPromptSubmit?") to slot a fifth host into without reactively hardcoding another special case under time pressure.

**Target files/layers.** `scripts/generate-subagent-artifacts.ts` and `scripts/install-harness.sh`'s host-detection table; a new short ADR or `docs/adding-a-host.md` naming the capability-predicate contract a fifth host adapter must satisfy before code is written, referencing the exact quirk classes ai-memory's report documents (SessionStart-stdout-discarding hosts, passive-UserPromptSubmit hosts).

**Why it matters here.** This is explicitly named in the task brief as a cross-cutting theme worth watching for ("managed-harness adapters for new agent hosts (Kimi Code, Grok — massa-ai currently ships Claude/Codex/Cursor/OpenCode)"). It is deliberately scoped here as *preparatory* work, not "go build a Kimi Code adapter" — there is no evidence of user demand for a specific fifth host today, so building the adapter itself would be premature; preparing the abstraction so the *next* one is cheap is the right-sized version of this port.

**Public-compatibility blast radius.** Medium if done carelessly — `scripts/generate-subagent-artifacts.ts` and the installers are explicitly named public-compatibility surfaces in `CLAUDE.md` ("Installers, hooks, generated config, and symlinks are public compatibility surfaces — treat a change to them as breaking until proven otherwise"). Scope any refactor to be a pure extraction with zero behavior change for the four existing hosts.

**Deterministic verification.** `scripts/__tests__/subagent-parity.test.ts` continues to pass unchanged for all four existing hosts after the refactor (a regression-only gate proving no behavior moved); a fixture "host 5" exercised only in the test harness (never shipped) proves the capability-predicate path is real and not just a naming exercise.

### PORT-07 — Shared RSS/memory-delta test helper (rank 7)

**Mechanism.** cbm's memory-diagnostics framework (three-way OS-committed/tool-visible/residual memory map; issue #581's ~70-commit investigation) is mostly not portable as-is (native Windows heap census, mimalloc TLS callbacks — see Not portable), but the underlying design principle it states explicitly — "an incomplete map announces itself instead of looking balanced" (a blind spot should show up as a growing residual number, not default to a falsely-reassuring zero) — is generic. massa-ai already practices a *scaled-down* version of this twice, ad hoc: the 16 MiB disposal-stress native-retention test (MLTS-022, per `README.md`/`FEATURES.md`) and Wave 5's Tarjan-SCC RSS guard (`design.md` AC-2: "< 16 MiB over baseline... input-size-linear allocation... expected and bounded"), each independently measuring an RSS delta against a stated baseline rather than merely asserting "no leak."

**Target files/layers.** A small shared helper, e.g. `packages/core/src/__tests__/helpers/rss-delta.ts`, exposing a `measureRssDelta(baseline, fn)` primitive so a *third* native/allocation-heavy subsystem (there will likely be one, given massa-ai's native tree-sitter surface keeps growing per `CLAUDE.md`'s multi-language breadth notes) doesn't reinvent the idiom a third time.

**Why it matters here.** Lowest-ranked of the seven because it is not solving a live problem — it is DRY-ing an already-correct, already-duplicated-exactly-twice pattern before a third duplication happens.

**Public-compatibility blast radius.** None (test-only helper).

**Deterministic verification.** Both existing call sites (MLTS-022, Wave 5 cycle-detection) refactored to use the shared helper with no change in reported numbers.

## Rejected / deferred

- **R-01 — Mandatory per-account background coordination daemon** (cbm PR #1139). REJECT. massa-ai already solved the *same* underlying problem — single-writer coordination for concurrent indexing across independent MCP-client processes — via PostgreSQL-backed CAS leases (A-02, Wave 5 `managed_runs`) at a small fraction of the complexity a persistent daemon with its own wire protocol, admission-barrier ABI, and platform-specific IPC transport (Unix sockets vs. Windows named pipes) would cost. Building a daemon here would trade a solved problem for a much larger one — cost ≫ value.
- **R-02 — Flag-based CLI auto-generated from JSON Schema** (cbm §Features 3). DEFER. massa-ai's MCP tools are invoked by the agent host over the MCP protocol, not by a human typing shell commands against a general-purpose local daemon+CLI binary the way cbm's users do. The existing `--config-show`/`--config-init`/`--help` flags on `@massa-ai/mcp-client` already cover the realistic human-CLI surface. Revisit only if a debugging/ops workflow specifically needs direct human invocation of individual tools.
- **R-03 — VirusTotal/AV-evasion binary hardening** (cbm PR #1316/#1328/#1332/#1338/#1340/#1341/#1344 — the launcher removal, in-process-updater removal, ELF `noexecstack`, macOS `strip` fallback, binary-composition gate). REJECT — not applicable. massa-ai ships no compiled/signed binary; its distributables are TypeScript source plus an npm package run under Bun/Node, with no PE/ELF/Mach-O artifact for VirusTotal or Windows Defender to score. The transferable *governance lesson* ("an in-process self-updater is structurally a downloader, and that shape alone eventually draws scrutiny — print the exact command instead") is captured as L-02 below, since massa-ai's installers already avoid this trap (they run explicit, visible scripts rather than silently self-updating in-process) but it is worth writing down before anyone adds a self-update feature.
- **R-04 — Prerelease npm dist-tag / GitHub prerelease channel gating** (cbm PR #1303). DEFER. massa-ai's `scripts/release-version.ts` derives versions strictly from `CHANGELOG.md` headings and has no prerelease/`-rc.N` concept in its versioning scheme today (`CONTRIBUTING.md` §CHANGELOG authoring). Only relevant if massa-ai adopts a prerelease channel, which is not currently planned or requested.
- **R-05 — The specific Kimi Code / Grok Build CLI stdout-quirk workarounds** (ai-memory `526f4bd`, `9c6a2ab`, `d4585a5`). DEFER as literal code — these are facts about two specific hosts massa-ai does not currently integrate. Captured instead as the generalized preparatory work in PORT-06, which is the right-sized version of "be ready for this," rather than building an adapter for a host with no demonstrated demand.

## Not portable (stack-specific)

Grouped by theme, one line each:

- **Windows/native-binary AV surface:** launcher/payload binary split + Defender ML dropper false-positive (cbm PR #1316); Windows named-pipe IPC + `CLOSE_INTENT` frame for no-half-close platforms; ARM64 SQLite alignment crash; mimalloc TLS-callback (`.CRT$XLB`) thread-heap release under static MinGW; BSD-vs-GNU `mktemp` template quirks; MSYS2-specific CI plumbing — all native/cross-platform-C-toolchain-specific; massa-ai's runtime is Bun/Node with no vendored allocator, no Windows build target, no code-signing surface.
- **ELF/binary hardening:** missing `.note.GNU-stack` → executable-stack fix, `-Wl,-z,noexecstack`; macOS `strip -x` vs. bare `strip` symbol-clearing mismatch; `SQLITE_OMIT_LOAD_EXTENSION` compile flag; reproducible-build timestamp flags (`-Wdate-time`) — all compiled-binary concerns with no analog in a Bun/TS package.
- **`cargo install --path`-without-lockfile CI regression class** (ai-memory `5405cc7`, new `source-install` CI job) — a Rust/Cargo unlocked-dependency-resolution gap; massa-ai's `bun install --frozen-lockfile` already pins deterministically in every job by construction, with no unlocked-install code path to regress.
- **`rmcp` 1.7→1.8 dual-role stdio↔HTTP MCP bridge plumbing** (ai-memory `e3c3314`/`5405cc7`) and **`StoredOAuthToken<E>` generic OAuth-refresh envelope unification** — Rust-crate-internal; massa-ai's MCP transport is the TypeScript `@modelcontextprotocol/sdk`, and it has no OAuth-token-refresh subsystem of that shape to unify.
- **Docker CLI wrapper stdin/TTY flag logic** (`bin/ai-memory`'s `-i`/`-t` detection bugs, SELinux `label=disable`, completion-pipe-closure) — massa-ai's Docker story is a documented `docker compose run --rm -i mcp` invocation, not a bespoke wrapper script with the same class of TTY-detection bug surface.
- **SQLite `WITHOUT ROWID` + trigger-based scope-integrity checks** (ai-memory's `session_consolidation_jobs` `BEFORE INSERT` trigger) — the *pattern* (a DB-level integrity constraint, not just an app-level check) is generic and arguably already present in massa-ai's Postgres `CHECK`/partial-unique-index constraints (Wave 5's `managed_runs` table has both), but the literal SQLite trigger syntax is not portable and not needed given Postgres already has richer constraint mechanisms in use.
- **Antigravity CLI tool-family/path-key extraction fixes** (ai-memory `94e0f5c`/`6451beb`) — specific to a third-party hook-payload shape (`toolCall.args.CodeContent` nesting) massa-ai does not parse; no Antigravity integration exists.
- **OpenAI-compat `strict` JSON-Schema structured-output default flip** (ai-memory `75ff81f`) — massa-ai already gates structured output differently (a version-capability check, `_checkJsonSchemaSupport`, per Wave 7 W7-07) rather than a blanket `strict`-by-default flip; the mechanisms don't map cleanly enough onto each other for a clean lift.
- **MSIX-packaged Claude Desktop config-path detection** (ai-memory `b8f8316`/`41928d8`) — Windows-packaging-specific; massa-ai's own `claude-desktop` config-path handling (`scripts/install-agents.sh`) is explicitly macOS-only.
- **`CLAUDE_CONFIG_DIR` relocation support across three independent installer commands** (ai-memory `aab94b5`/`4760311`/`4efe608`) — the underlying lesson (centralize config-path resolution once) is exactly A-04's already-shipped pattern; the specific env var and Claude-Code-relocation mechanics are host-specific plumbing massa-ai's installers would only need if Claude Code's own config-relocation behavior changes, which is outside this repo's control to anticipate speculatively.
- **Graph-UI Vite dev-server Origin-allowlist hardening + "kill arbitrary process" capability removal** (cbm, daemon-owned UI) — NOT APPLICABLE rather than not-portable in principle: massa-ai's Web UI is documented as read-only by construction with a static-scan test verifying no mutating endpoint is ever called (`FEATURES.md` §Web UI & Dashboard), so there is no "kill process" capability to remove in the first place, and CORS is already an explicit allowlist (`CHANGELOG.md` 1.8.0, audit-remediation-2026-07 SEC finding) — both risks this cbm change addresses are already closed here by a different, already-shipped route.
- **Directory-discovery hard stack cap → realloc-growable fix** (cbm PR #1230, `WALK_STACK_CAP 512`) — the underlying bug class is a fixed-size C array; massa-ai's `discover.ts` uses ordinary dynamically-growing JS arrays/data structures throughout (confirmed by reading the file and grepping for `cap|MAX_|limit|stack` — the only bound present is `MAX_MATCH_WORK`/`MAX_IGNORE_PATTERNS` in the unrelated Wave-5 capture-policy module, which bounds ignore-*pattern-matching work*, not directory-walk breadth), so the entire bug class has no substrate to occur on in this language.
- **Parallel-vs-sequential pipeline edge-type divergence** (cbm PR #1230, `INHERITS` vs. `IMPLEMENTS`) — checked directly: massa-ai's structural/symbol extraction has no `INHERITS`/`IMPLEMENTS` edge-type vocabulary at all (zero grep hits in `packages/core/src/services/structural`), and while `pipeline.ts`/`discover.ts`/`load.ts` do use "parallel" in the sense of concurrent file processing, there is no evidence of *two independently-implemented extraction code paths* (a "parallel pipeline" vs. a "sequential pipeline") that could diverge on a classification decision the way cbm's did — the bug's precondition doesn't exist here.

## Lessons to record

Drafted to match `.specs/LESSONS.md`'s existing candidate format (machine-owned via `lessons.py`; these are **proposed text** for the maintainer to feed through that pipeline, not a direct edit to `lessons.json`):

- **L-DRAFT-A** — An in-process self-updater is structurally a downloader (fetch, verify, extract, exec); that shape alone eventually draws AV/heuristic scrutiny on a shipped binary, or should be avoided on privacy/network-hygiene grounds even absent AV. Prefer printing the exact install/upgrade command over silently fetching-and-executing it in-process. (massa-ai's installers already do this correctly — no self-update-in-process code exists — but it is worth writing down before anyone adds one.) — evidence: `codebase-memory-mcp` PRs #1316/#1332/#1338.
- **L-DRAFT-B** — When retiring a compatibility boundary (env-var prefix, config key, feature flag), assert **both** directions in one test: the new name reaches its target, and the old name has zero effect. A suite that checks only the new name still passes if the old one is silently left wired up beside it. — evidence: `packages/shared/src/config/__tests__/llm-env-prefix.test.ts` (massa-ai's own, already-correct instance); `codebase-memory-mcp` PR #1341's grep-tripwire is the same idea in a weaker form.
- **L-DRAFT-C** — A CI job's own ephemeral package-manager cache that is never round-tripped through a persistent cache action will occasionally race a native-addon post-install script on a cold runner; the fix that actually holds is a warmed/persistent cache, not a reactive purge-and-retry — but keep the purge-and-retry as a fallback even after adding warming. — evidence: `.github/workflows/ci.yml:64-86`'s own documented v1.4.0 incident; `codebase-memory-mcp`'s `cache-warm.yml`.
- **L-DRAFT-D** — A CI workflow deliberately isolated from another for a release-chain-triggering reason can silently also isolate *test coverage*, not just the release trigger. Audit which env-gated test suites the isolated workflow alone exercises, and either also exercise them in the main gate or write down explicitly that the isolated workflow is the sole correctness gate for that subset. — evidence: `ci.yml` vs. `coverage.yml`'s `RUN_POSTGRES_TESTS` divergence (this report, DB-07).
- **L-DRAFT-E** — Passive/automatic data capture (hook-based observation capture, telemetry, session recording) needs a type-enforced sanitization boundary — a wrapper type only constructible by passing through a scrubber — in place *before* the first byte of real user data reaches durable storage. Retrofitting it after users have already run with the unsanitized path is a materially bigger, riskier change than building it in from the start. — evidence: `ai-memory`'s 3-PR retrofit arc (issue #196); massa-ai's own currently-unsanitized Observation path (this report, DB-08/PORT-02).
